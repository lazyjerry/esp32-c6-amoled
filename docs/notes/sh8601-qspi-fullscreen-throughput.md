## 結論
本板 368×448 RGB565 全螢幕（329,728 bytes）用 `esp_lcd_panel_draw_bitmap` 裸繪的實測：

| 分段高度 | 平均 | fps | 吞吐 |
|---|---|---|---|
| 16 列 | 44 ms | 22.5 | 7.09 MB/s |
| 32 列 | 41 ms | 23.9 | 7.51 MB/s |
| **64 列** | **32 ms** | **30.7** | 9.67 MB/s |
| 112 列 | 28 ms | 35.3 | 11.10 MB/s |

**分段越大越快**，因為每段都有固定的指令與位址開銷。但收益遞減：
64→112 列只快 4ms，緩衝卻要從 94KB（368×64×2×2，雙緩衝）漲到 165KB。
**64 列是 RAM 與速度的平衡點**，現行設定不必改。

**更重要的一條：動畫的瓶頸不在傳輸。**
全螢幕傳輸上限是 31 fps（64 列），而擲筊動畫實測只有 21 fps，
而且它只畫兩片 132×140 的 sprite，傳輸量遠小於全螢幕。
所以要提升動畫流暢度，該優化的是 **LVGL 的算圖成本**（sprite 格式、
旋轉縮放的每像素運算），不是加大繪圖緩衝或換更快的匯流排。

## 為什麼
- QSPI 每次 `draw_bitmap` 都要送一輪 column/row address set 指令再送像素，
  段數越多，這筆固定開銷被重複越多次
- 沒有 PSRAM，330KB 的整張 frame buffer 放不進 512KB SRAM，所以一定得分段，
  問題只在分幾段
- 11.10 MB/s（112 列）已接近這條 QSPI 的實際上限，再往上不會有空間

## 驗證
`docs/examples/verify_s4.c`（測完歸檔）。要複現就把它放回 `src/`，
搭配 `scripts/one-time/gen-testcard.py`（一次性腳本，不進版控）產的 330KB 測試圖，
`pio run -e verify-s4 -t upload` 之後讀序列埠。
用真圖而非小圖重複送——小圖會被 flash 快取命中，量出來偏樂觀。
