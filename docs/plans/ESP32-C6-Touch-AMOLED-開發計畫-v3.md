## 0. 這一版改了什麼

v2 的產品定位（Ritual Loop，不做掌上算命機）與絕大多數技術裁決都保留。這一版只改兩件事，但這兩件事動到地基：

1. **整條 Wi-Fi 路線刪除。** 裝置全生命週期不連網，v2 排在 v2/v3 的 Wi-Fi、OTA、雲端 AI 解籤代理全部移除，不是延後。
2. **內容改為預先產好燒進機身 flash。** 原本要靠網路才拿得到的東西（AI 解籤內容、字型、擴充語料、圖與音效）改為在 Mac 上事先產好，寫進 `storage` 分區的 SPIFFS，更新走 USB 重燒。

### 2026-08-29 修訂：記憶卡路線已被實測推翻

初版 v3 把 microSD 當成內容通道。**M0/S1 實測證明這片板子沒有連通到 ESP32 的 microSD 卡座**——拔卡與插卡各掃一次全部可用 GPIO，20 支腳位零差異，卡片與 SoC 之間沒有任何電氣連結。完整過程見 [M0/S1 驗證紀錄](../knowledge-skill/M0-S1_SD卡與SPI2分時共用驗證-001/notes.md)。

「不上網」是目的，記憶卡只是手段。手段換成 SPIFFS + USB 更新，目的不變，而且更簡單——沒有 SPI 衝突、沒有匯入流程、沒有無卡降級路徑。

同一次驗證也留下一個有價值的正面結論：**`SPI2` 可以安全地拆掉再裝回去**（§8 S1 子項③），這是未來在這片板子上加任何 SPI 周邊的前提。

### 1.2 本次由 ESP-IDF 查證的三條 SoC 事實

來源是本機 `framework-espidf` 的 `components/soc/esp32c6/include/soc/soc_caps.h` 與 `hal/spi_types.h`，非規格頁推測：

| 事實 | 依據 | 對設計的意義 |
|------|------|------|
| **C6 無 SDMMC host** | `SOC_SDMMC_HOST_SUPPORTED` 未定義（全 IDF 只有 esp32／esp32s3／esp32p4 有） | SD 卡**只能走 SPI 模式**（`sdspi`），拿不到 4-bit 匯流排頻寬 |
| **可用 GP-SPI 只有一個** | `SOC_SPI_PERIPH_NUM = 2`，而 `SPI1_HOST` 屬 flash；`SPI3_HOST` 在 `> 2` 才編入 | 使用者可用的只有 `SPI2_HOST` |
| SDIO 只有 slave | `SOC_SDIO_SLAVE_SUPPORTED = 1` | 不能拿來當卡片主機 |

### 四條會改變設計的限制

**限制 A：沒有 PSRAM，動畫預算極小。**
368×448 全螢幕 frame buffer 需要 330KB，配不下（[sh8601-lvgl9-area-rounding.md](../notes/sh8601-lvgl9-area-rounding.md)）。現行 LVGL 用 368×64 雙緩衝（92KB）。既有的擲筊動畫**實測 21 fps**（2140ms / 46 幀），而那只是兩片半月 sprite 在小範圍內移動。
→ 全螢幕緩慢煙霧、燭火、神像淡入在這片板子上做不到。動畫必須限制在小矩形內。

**限制 B：觸控沒有手勢，要自己算。**（2026-08-29 已解決）
這顆晶片只是 I2C 位址與 FT5x06 相同，套官方元件會把它寫到不回應 I2C（[touch-not-real-ft5x06.md](../notes/touch-not-real-ft5x06.md)）。可用的只有：從 `0x02` 連讀 5 bytes 拿到單點 X/Y，20ms 輪詢。
→ 已在 [touch.c](../../src/touch.c) 自行接成 LVGL indev 並自寫 swipe 判定。實測座標與面板 1:1，判定門檻為橫移 ≥90px、橫移 > 縱移 ×2、700ms 內。判定成立時必須 `lv_indev_reset()` 取消該次觸碰，否則滑過按鈕會被當成點擊——見 [touch-swipe-must-cancel-lvgl-press.md](../notes/touch-swipe-must-cancel-lvgl-press.md)。

**限制 C：日常使用的電源模型只有一種。**
BOOT 在 GPIO9，不是 LP IO，喚不醒 deep sleep；PWR 直通 AXP2101（[esp32c6-boot-key-cannot-wake-deep-sleep.md](../notes/esp32c6-boot-key-cannot-wake-deep-sleep.md)）。
→ 實際流程是：**按 PWR 開機 → 走完流程 → 軟關機**。所以**開機到正殿的時間是產品體驗的一部分**，目標 2 秒內。

**限制 D（2026-08-29 改寫）：沒有記憶卡可用，且 SPI2 只有一個。**

兩件事，一件是實測結論，一件是 SoC 事實：

1. **板上沒有連通的 microSD 卡座。** 拔卡與插卡各掃一次 GPIO 0~23（跳過 I2C、USB、flash），20 支腳位電位**零差異**。一張卡插進卡座至少會在資料線上造成可測量的阻抗變化，全無反應代表沒有連結。BSP 標頭寫的 SD 腳位涵蓋整個產品線，不代表手上這片的實際配置。
2. **可用的 GP-SPI 只有 `SPI2_HOST`**（§1.2），已被 LCD 佔用（`#define LCD_HOST SPI2_HOST`，SCLK=0 / CS=5 / D0~D3=1,2,3,4）。即使日後外接 SPI 周邊，也得和面板分時共用。

→ 所以**所有內容都燒在機身 flash 裡**，更新走 USB。設計見 §5.2。
→ 分時共用的可行性已經驗過並通過（§8 S1 ③），未來要外接 SPI 周邊時直接沿用 `board_panel_deinit()` / `board_panel_init()`。

## 3. 產品範圍

### 保留的核心

```
入廟 → 參拜 → 稟告 → 求籤 → 擲筊確認 → 解籤 → 留下紀錄 → 離廟
```

### v1 的完整定義

**一台永不連網的單機儀式裝置。** 開機即正殿，所有內容都燒在機身 flash 裡。

v1 相對 v2 企劃「多」了什麼：AI 語感的解籤內容回到 v1（因為改成預產）。
v1「少」了什麼：即時性。內容要換得接 USB 重燒 storage 分區，不會自己更新。這正是換來開機快、無後端、無金鑰、無隱私問題的代價。

### v2／v3

- **v2**：內容擴充（更多籤詩、更多解讀角度）。原本規劃的 RTC 相關功能（農曆、初一十五、參拜日期、日夜氛圍）已砍除，理由見 §8 S2
- **v3**：語音稟告（前提是 §7 S7 通過）、多神明

沒有 Wi-Fi 里程碑。

## 5. 技術架構

### 5.1 從單畫面狀態機改成畫面管理器

沿用 v2。現行 [main.c](../../src/main.c) 是一支 `while(1)` 直接管擲筊的狀態，加到 8 個畫面後撐不住。

改成：每個畫面提供 `enter / exit / tick / on_event`，由一支 `screen_mgr` 持有目前畫面；輸入（觸控、IMU 手勢、BOOT、PWR）統一收在主迴圈，轉成事件送給目前畫面。PWR 軟關機維持全域攔截。現有的 `cast_ui.c` 改成實作這組介面的其中一個畫面，內部動畫邏輯不動。

### 5.2 內容怎麼進到裝置裡

v3 初版設計了一套「開機時從 microSD 匯入 SPIFFS」的流程。**M0/S1 實測證明板上沒有連通的卡座**，這套流程整個拿掉。

**現行做法：內容在建置時產生成 SPIFFS image，跟韌體一起燒進去。**

```
Mac 端                                    裝置
──────                                    ────
語料 JSON ─┐
AI 預產解讀 ├─ scripts/gen-content.sh ─→ storage.bin ─(USB)─→ storage 分區
UI 字串    ─┘         │                                          │
                      └─ 掃出字集 ─→ gen-font.sh ─→ src/fonts/*.c ┴─→ app 分區
```

執行期只有一件事：開機掛載 SPIFFS，讀 JSON。沒有匯入、沒有版本比對、沒有無卡降級路徑、沒有進度畫面。

**更新內容的代價**：要接 USB 重燒 `storage` 分區。對一台開發者自用的裝置，這不是問題；真正被換掉的只是「不接電腦就能換內容」這一項便利。

**燒錄只動 storage 分區**，不必重燒整支韌體。不能用 `pio run -t buildfs / uploadfs`——
PlatformIO 不產生也不燒 SPIFFS 映像，見 [筆記](../notes/pio-does-not-build-or-flash-spiffs.md)：

```bash
./scripts/gen-content.sh      # data/*.json → spiffs_content/ 與 .pio/storage.bin
./scripts/flash-content.sh    # 只燒 storage 分區，不動韌體
```

### 5.3 資料層

| 資料 | 執行期存放 | 來源 | 理由 |
|------|------|------|------|
| 籤詩 + 傳統解籤 | SPIFFS `storage` | 建置時燒入 | 11MB 空著；`espressif/cjson` 已是相依 |
| **AI 預產解讀**（60 籤 × 6 類別） | SPIFFS `storage` | 建置時燒入 | 純查表，裝置端不生成 |
| 子集字型 | app 分區 const 陣列 | `gen-font.sh` 從語料掃字集產生 | 見 §5.4 |
| 正殿背景／神像圖 | app 分區 const 陣列 | `gen-sprites.sh` | flash 可直接定址，LVGL 從 flash 畫圖不吃 RAM |
| 音效 | app 分區 const 陣列 | `gen-sound.sh` | 沿用現行 `src/sounds/` 做法 |
| 參拜紀錄 | NVS | 執行期產生 | 筆數小、要抗斷電。**只存序號與筊象，不存日期**，見 §8 S2 |
| 設定（音量、亮度） | NVS | 執行期產生 | 同上 |

字型放 app 分區而非 SPIFFS，是因為字型與韌體綁定（LVGL 版本、`lv_font_conv` 產出結構）。**內容擴充到新字時必須連韌體一起重燒**——`gen-content.sh` 掃出字集後會直接觸發 `gen-font.sh` 重產，兩者一起進版控，不會脫節。

### 5.4 字型：v2 的最大技術風險在這一版消失

v2 §5.3 把 AI 解籤移出 MVP 的**主要技術理由**是：模型回什麼字無法預知，子集字型必然缺字，畫面出現豆腐方塊。

**改成離線預產後，這個理由不成立了**：所有會顯示的字都在內容包裡，可以在 Mac 上掃出完整字集再產字型。

實測基準（`src/fonts/font_zh_28.c`）：147 個中文 + ASCII，`glyph_bitmap` 共 59,853 bytes。換算：

| 字級 | 每字約 | 1,500 字 | 2,500 字 | 4,808 常用字 |
|------|------|------|------|------|
| 20px 4bpp | ~190 B | ~285 KB | ~475 KB | ~0.91 MB |
| 24px 4bpp | ~270 B | ~405 KB | ~675 KB | ~1.30 MB |
| 28px 4bpp | ~375 B | ~560 KB | ~940 KB | ~1.80 MB |

60 籤傳統解籤估 1,200~1,500 相異字；加上 360 篇 AI 預產解讀，估到 2,000~2,500 相異字。**24px 全部收進來約 675KB，4MB app 分區放得下**，S5 負責量實際值。

**必須同時改腳本**：`gen-font.sh` 目前把字集寫死在腳本裡的字串變數。內容包進來之後這樣維護不了，要改成**從內容包 JSON 與 UI 字串檔掃出字集**，內容一改就重產。改字串卻忘了回頭改腳本，結果就是豆腐方塊。

### 5.5 記憶體預算

沒有 PSRAM，512KB SRAM。**刪掉 Wi-Fi 後只剩一套配置**：

| 情境 | LVGL 繪圖緩衝 | 備註 |
|------|------|------|
| 全程（v1） | 368×64 雙緩衝 = 92KB | 實測可跑 |

不再需要為 TLS handshake 讓出堆積，`sdkconfig.defaults` 裡為連網準備的 mbedTLS 縮小設定與 `MBEDTLS_DYNAMIC_BUFFER` 可以在確認無其他相依後移除，順便縮小韌體。

實際餘裕要在 M0 用現有的 log 量測後填回本表：

```
I (xxx) app: 就緒，剩餘堆積 xxxxx bytes
```

### 5.6 動畫預算

沿用 v2，未改動。錨點是實測值：擲筊 46 幀 / 2140ms = **21 fps**。

全螢幕重繪一次要送 329,728 bytes 過 QSPI，加上 LVGL 算圖，粗估單幀 30~40ms（**未實測**）。所以：

- 全螢幕動畫：**不做**
- 局部動畫：控制在 200×280 以內（~112KB／幀）
- 正殿香煙：~120×160（~38KB／幀），10 fps 即可

`gen-sprites.sh` 已經在產筊杯圖，香煙／籤筒沿用同一支腳本擴充，**產物一律不手改**。

**硬規則：動畫一律用 sprite ＋ 旋轉縮放，禁止逐幀點陣圖。**

上面的區塊尺寸限制管的是 RAM 與 fps，管不到 flash。逐幀圖的 flash 成本是尺寸乘上幀數，
會直接吃掉 app 分區：籤筒 180×280 一幀就是 100,800 bytes，十幀就是 1MB。

現行擲筊動畫是這條規則的範本——畫面上 46 幀，flash 裡只有兩張圖
（`blk_flat_map` / `blk_round_map`，各 36,960 bytes），幀是算出來的。

### 5.7 Flash 空間預算（2026-08-29 實測）

分區從 `app 4MB + storage 11MB` 改為 **`app 6MB + storage 9MB`**（[partitions.csv](../../partitions.csv)）。
原本的配置是反的：語料吃不到 1MB 卻分到 11MB，而圖與字型全部擠在 app 分區。

**基準值取自編譯產物的符號表**（`riscv32-esp-elf-nm --print-size`），不是估的：

| 符號 | 實際大小 | 換算 |
|------|---------|------|
| `glyph_bitmap`（font_zh_28，147 中文＋ASCII） | 59,853 B | 每個中文字 @28px ≈ 375 B |

| 項目 | 估算 |
|------|------|

## 6. 內容包規格

原始語料放在 [data/](../../data/)（進版控、人工編輯），產物由
[scripts/gen-content.sh](../../scripts/gen-content.sh) 產生到 `spiffs_content/`（不進版控、不手改）：

```
data/                          spiffs_content/
  poems.json        ─┐           poems.json      裝置端查表用的精簡結構
  readings.json      ├─ gen ─→   readings.json
  ai_readings.json  ─┘           ai_readings.json
                                 charset.txt     掃出的相異字，供 gen-font.sh 產子集字型
```

### 籤詩來源與校對狀態

籤系是**六十甲子籤**，**63 首**（60 首正籤＋頭籤、籤首、籤王三支額外籤，後三支沒有干支）。

**63 首的本文已全數核對完成**（2026-08-29，逐首程式比對使用者提供的
`data/temples-fs60.csv`，籤詩、干支、卦象、屬性方位 63/63 相符）。
`data/poems.json` 的每首都帶 `verified` 欄位，`gen-content.sh` 會在有
`text: null` 或 `verified: false` 時警告：

| 欄位狀態 | 意義 |
|------|------|
| `text: null` | 沒有把握，**刻意留空不編造** |
| `verified: false` | 有內容但尚未核對，用字可能有出入 |
| `verified: true` | 已核對。**上產品前必須全部為 true** |

### 為什麼語料一律來自實際資料、不靠 AI 記憶

本專案實測過。拿 AI 憑記憶產出的 9 首與真實資料逐句對照，
**只有 3 首完全正確，正確率 33%**，三種錯誤型態一種比一種難發現：

| 型態 | 例子 | 為什麼難抓 |
|------|------|-----------|
| 用字出入 | 第 7 籤四句看似全對，實際三處用字不同 | 讀起來完全通順 |
| 張冠李戴 | 第 27 籤寫的是第 47 籤的內容 | 單看那首完全正確，只有比對籤號才發現 |
| 字元污染 | 第 5 籤 `鬼神дось難測度` 混入西里爾字母 | 幾百句中文裡肉眼看不出來，會變成豆腐方塊 |

另外 AI 推導的干支序也是錯的——六十甲子籤走**六甲旬序**（甲子、甲寅、甲辰…）
而非干支順序，第 2 籤是「甲寅」不是「乙丑」。

因此有兩道機制：`gen-content.sh` 的字元白名單守門（ASCII、一般標點、
幾何符號 `○●`、CJK），違反就**中止**而不是警告；以及沒把握的欄位一律留 `null`。
編出來的假籤混在真的裡面，是校對時最難發現的錯誤。

### 來源與版權界線

`temples.tw` 的 `robots.txt` 明確 `User-agent: ClaudeBot / Disallow: /`，並宣告
`Content-Signal: search=yes, ai-train=no, use=reference`（載明為 EU 2019/790 第 4 條的
權利保留）。**本專案的自動工具不抓該站**；`data/temples-fs60.csv` 是使用者自行擷取後提供的。

即使資料在手，仍要劃清界線：

| 欄位 | 進不進產品 | 理由 |
|------|-----------|------|
| 籤詩本文、干支、卦象、屬性方位 | **進** | 公有領域的傳統籤譜資料，各宮廟通用 |
| 籤詩語譯、籤意、故事、籤解 | **不進** | temples.tw 編寫的內容，屬該站著作 |

CSV 全文留在 `data/` 供人校對，但 `poems.json`、SPIFFS 與韌體都只收上表的前一列。
產品要的白話解讀是離線自產的 `ai_readings.json`，本來就不依賴外部來源。

**不需要 manifest**。v3 初版設計的 `content_version` / `min_firmware` / `charset_hash` 全部是為了「裝置要判斷外部媒體上的內容能不能吃」而存在的；內容改成跟韌體一起建置之後，版本天生一致，這層防護沒有守備對象。

執行期讀不到檔案就是建置出錯，不是需要優雅降級的情境——直接 log 錯誤並顯示提示畫面，讓人回去重燒。

| **BOOT 短按＝主要動作，長按＝回正殿** | 原本半數畫面把短按當返回、半數當功能鍵，同一顆鍵在不同畫面做相反的事。改成長按（900ms）在任何畫面都回正殿，短按只做該畫面的主要動作，沒有主要動作的畫面就不接。長按按滿就發、不等放開，手指還壓著就看得到畫面切走 |
| **籤詩一句一行** | 語料的本文是全形空白分隔的四句，交給 LVGL 自動折行會斷在句子中間。顯示前把分隔符換成換行 |

#### 導覽的實際接法

企劃 §4 的圖是流程，這裡是輸入怎麼對應到流程：

| 畫面 | 觸控 | IMU | BOOT 短按 | BOOT 長按 |
|---|---|---|---|---|
| 正殿 | 點擊 → 三拜；左右滑 → 側翼 | — | 自由擲筊（跳過儀式） | — |
| 三拜 | — | 前傾 ×3 | 一拜（與前傾等價） | 回正殿 |
| 稟告 | 點格子 → 求籤 | — | — | 回正殿 |
| 求籤 | 左右滑 → 正殿 | 搖動 → 抽籤 | 抽籤／籤號停著時進擲筊 | 回正殿 |
| 擲筊 | 左右滑 → 正殿 | 搖動 → 擲；左右晃 → 收結果 | 擲／收結果 | 回正殿 |
| 解籤閣 | 上下捲動；「回正殿」鈕 | — | — | 回正殿 |
| 參拜簿／設定 | 左右滑 → 正殿 | — | — | 回正殿 |
| 語料錯誤 | — | — | — | — |

三條規則就講得完：**短按做這個畫面的主要動作、長按離開、語料錯誤是刻意的死路**。
三拜的主要動作就是拜，所以短按算一拜，按三次與前傾三次走到同一個地方——
手上接著 USB 或坐著測的時候晃不動板子，儀式不該因此走不完。
動畫跑到一半（擲筊在空中、籤筒在抖）時長按與左右滑都不放行，否則動畫的 timer 會繼續在看不見的畫面上跑。

**正殿的 BOOT 刻意保留自由擲筊**——原本的擲筊功能不因為多了儀式就消失，測試時也不必每次走完三拜。

**這組數字改變了 §11 待處理的優化方向**：全螢幕傳輸上限是 31 fps，
而擲筊動畫只有 21 fps，且它只畫兩片 132×140 的 sprite、傳輸量遠小於全螢幕。
**瓶頸在 LVGL 算圖，不在傳輸也不在緩衝大小。** 64→112 列只快 4ms，
緩衝卻要從 94KB 漲到 165KB，不值得。詳見
[筆記](../notes/sh8601-qspi-fullscreen-throughput.md)。

**S5 通過。** 收錄語料字集後（`charset.txt` 475 字，加上 UI 字串共 552 個相異字符）：

| 字型 | 字符數 | `glyph_bitmap` | 每字 |
|---|---|---|---|
| `font_zh_16` | 651 | 65,905 B | 101 B |
| `font_zh_28` | 651 | 192,956 B | 296 B |

韌體 745,442 → **932,830 bytes**，佔 6MB 分區的 14.8%，**餘裕 5.1MB**——
通過條件是「加背景圖後仍有 1MB 以上」，大幅達標。

### S2 的處置（2026-08-29）

**第一段通過，第二段決定不驗，直接採用不通過的處置。**

第一段（驅動可用性）實測結果，[rtc.c](../../src/rtc.c) 新寫的 PCF85063 驅動：

```
rtc: PCF85063 就緒，Control_1=0x00
s2: ① 振盪器停止旗標：有停過        ← 首次上電，符合預期
s2: ② 時間不可信，已設為 2026-08-29 10:00:00
s2: ④ 5 秒後 10:00:05，相差 5 秒 → 走時正常
```

第二段是「AXP2101 軟關機十分鐘後時間還在不在」，需要拔 USB、按 BOOT、等待、按 PWR，
且**必須用電池跑**（USB 供電時 PMIC 切不掉電軌）。**決定不做這項驗證**，
直接採用不通過時的處置：

| 項目 | 決定 |
|------|------|
| 參拜紀錄 | **只存遞增序號 + 筊象 + 籤號，不存日期** |
| 農曆、初一十五、神明聖誕 | **整批砍除** |
| 日夜氛圍 | **砍除**（同樣需要可信時間） |
| 每日參拜狀態（今日是否已拜） | **砍除**——需要日期才能判斷「今日」 |
| PCF85063 驅動 | 保留在 `src/rtc.c`，已驗證可用，但**產品不依賴它** |

**為什麼這個取捨划算**：省下的是一項需要人守著、耗時十分鐘、且結果只有兩種的驗證；
換到的是整條路徑上不再有「時間可不可信」的分支——不必寫降級邏輯、
不必處理「RTC 說現在是 2000 年」的情況、參拜簿的顯示與排序也單純。

裝置的使用模型本來就是「按 PWR 開機 → 走完流程 → 軟關機」（限制 C），
一次開機就是一次參拜，用遞增序號表達「第幾次」在語意上也說得通。

日後若真的需要日期（例如要做農曆），再回頭補這項驗證即可，
驅動已經在了，屆時只要驗保時。

**M0 全部完成。** 下一步是 M1。

## 10. 明確不做

- **Wi-Fi、BLE、任何連網功能**——使用者決策。內容與韌體都走 USB 更新
- **裝置端呼叫 AI API**——沒有網路，且金鑰會跟著韌體外流。AI 解讀一律離線預產
- **SD 卡／任何外部儲存媒體**——實測確認板上沒有連通的卡座（限制 D）。內容燒進機身 flash，更新走 USB
- **全螢幕粒子／煙霧／燭火動畫**——沒有 PSRAM，做不到（限制 A）
- **八字／紫微／塔羅／星座／今日運勢**——會變成掌上算命機
- **聖筊率之類的統計**——會變成 Excel 宮廟

### 還沒換成美術的東西

**正殿的神像與神龕、求籤的籤筒與竹籤，全部是 LVGL 幾何佔位造型，不是美術**。
換成 `gen-sprites.sh` 產的圖只要改各畫面的 `build_screen()`，導覽、動畫時序與判定都不受影響。

### 已知的優化方向（依 S4 的實測修正）

擲筊動畫 21 fps，而全螢幕傳輸上限是 31 fps 且它只畫兩片小 sprite——
**瓶頸在 LVGL 算圖，不在傳輸**。所以要提升流暢度該做的是降低每像素的運算成本
（sprite 改 RGB565A8、預算好的影子圖），**不是**加大繪圖緩衝：
64→112 列只快 4ms，緩衝卻要從 94KB 漲到 165KB。
