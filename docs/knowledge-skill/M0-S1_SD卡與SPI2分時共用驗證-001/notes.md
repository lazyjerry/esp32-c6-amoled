# M0/S1 驗證紀錄

> 任務：驗證 SD 卡 sdspi 掛載，以及與 AMOLED 面板分時共用 SPI2_HOST 的可行性
> 對象：v3 企劃 §8 的 S1，四個子項
> 開始：2026-08-28　板子：`/dev/cu.usbmodem101`（實機在線）

這份是過程與決策紀錄，逐輪追加。壓縮過的結論另外寫進 `docs/notes/`。

---

## 背景：為什麼要驗這一項

v3 企劃把「掌上宮廟」改成全程不連網，記憶卡取代網路當內容通道。整條路線押在一個假設上：
面板與記憶卡可以分時共用同一個 SPI 控制器。

依據（本機查證，非規格頁推測）：

| 事實 | 來源 |
|------|------|
| C6 沒有 SDMMC host，SD 只能走 sdspi | `soc/esp32c6/soc_caps.h` 無 `SOC_SDMMC_HOST_SUPPORTED`（全 IDF 僅 esp32/s3/p4 有） |
| 可用的通用 SPI 只有 `SPI2_HOST` | `SOC_SPI_PERIPH_NUM = 2`，`SPI1_HOST` 屬 flash，`SPI3_HOST` 編在 `> 2` 條件裡 |
| 面板已佔用 SPI2 | `src/board.c` 的 `#define LCD_HOST SPI2_HOST` |

面板腳位 SCLK=0 / CS=5 / D0~D3=1,2,3,4；SD 腳位 CS=6 / CLK=11 / MOSI=10 / MISO=18。
腳位組無交集，`spi_bus_initialize()` 一次只能綁一組 → 不可能同時開著。

**S1 不通過，記憶卡路線整條作廢。**

## 第 1 輪：基準驗證（2026-08-28）

韌體 `src/verify_s1.c`，`pio run -e verify-s1 -t upload`，log 由 `scripts/monitor.sh 40 --reset` 取得。

### 結果

| 子項 | 結果 | 證據 |
|---|---|---|
| ① SD 掛載 | **失敗** | `sdmmc_init_sd_if_cond: send_if_cond (1) returned 0x108` |
| ② 拆 SPI 後畫面保持 | 未判定 | 需人眼，該輪無人在場 |
| ③ 面板重建 | **通過（程式面）** | `board_panel_deinit()` / `board_panel_init()` 皆 `ESP_OK`，`LCD panel create success` |
| ④ 吞吐量 | 未測 | ① 失敗，且卡上未放測試檔 |

原始 log 摘錄：

```
I (537) board: 板級初始化完成，面板 368x448
W (867) s1: ===== 請看螢幕：上紅下藍，白帶寫 STEP 1 =====
I (3867) s1: ② board_panel_deinit()：ESP_OK
E (10067) sdmmc_sd: sdmmc_init_sd_if_cond: send_if_cond (1) returned 0x108
E (10067) sdcard: 掛載失敗（ESP_ERR_INVALID_RESPONSE）
I (10067) sh8601: LCD panel create success, version: 2.0.0
I (10297) s1: ③ board_panel_init()：ESP_OK
W (16597) s1: 剩餘堆積 291572 bytes
```

### 判讀

**③ 通過是這一輪最重要的收穫**——SPI2 拆掉再裝回來在程式層面完全成立，
`esp_lcd_panel_del` → `esp_lcd_panel_io_del` → `spi_bus_free` → 換腳位重綁 → 重建面板，
整條鏈路沒有卡住的地方。企劃押的假設站得住。

**① 的失敗停在訊號層**：`send_if_cond` 是 SD 初始化的第一個握手（CMD8），
卡完全沒應答。這不是檔案系統、格式或頻率問題——卡根本沒說話。

使用者確認卡已插到底，所以問題在板子這一側。候選原因：

1. **SD 電源或控制腳掛在 TCA9554**——本板有前科：觸控 reset 掛在 TCA9554 bit5，
   冷開機被拉住就掃不到（見 `docs/notes/tca9554-holds-touch-reset.md`）。
   `board.c` 目前只操作 bit4（LCD reset）、bit5（觸控 reset）、bit7（喇叭功放），
   **bit0~3 與 bit6 從未動過**
2. **MISO 缺上拉**——IDF 的 sdspi 不會自動對 MISO 開上拉，板上若沒有外部上拉電阻，
   卡的回應讀不到
3. 腳位對應有誤（CS=6 來自既有筆記，CLK/CMD/DATA 來自 BSP 命名推導）

### 決策

先排 2 再排 1：MISO 上拉是一行設定、零副作用；TCA9554 拉 bit 有未知副作用，排後面。
腳位對應排最後，因為兩個獨立來源都指向同一組腳位。

## 第 2 輪：MISO 上拉 + TCA9554 探測（2026-08-29）

### 這一輪改了什麼

1. `sdcard.c`：`spi_bus_initialize()` 之後對 MISO 開內部上拉。
   **決策理由**：IDF 的 sdspi 不會自己拉 MISO，板上若沒有外部上拉電阻，卡的回應會讀成浮動值。
   永遠開啟而非做成選項——板上若已有外部上拉，內部上拉並存無害，沒有必要多一個開關。
2. `board.c`：新增 `board_exio_dump()` / `board_exio_drive()`，開放 TCA9554 的直接存取。
3. `verify_s1.c`：首次掛載失敗時自動探測，逐一累積拉高 TCA9554 的 bit0~3 與 bit6。
   **決策理由**：採累積而非逐一還原——本板 TCA9554 每個已知 bit 的高電位語意都是
   「放開 reset／通電」，累積不會關掉東西；且若要兩個 bit 同時拉高才通，逐一還原的試法找不到。

### 結果：全部失敗，且失敗方式完全一致

```
W s1: ① TCA9554 現況：config=0x4F output=0xFF input=0xF7
W s1: ① 累積拉高 0x01（剛加 bit0）→ ESP_ERR_INVALID_RESPONSE
W s1: ① 累積拉高 0x03（剛加 bit1）→ ESP_ERR_INVALID_RESPONSE
W s1: ① 累積拉高 0x07（剛加 bit2）→ ESP_ERR_INVALID_RESPONSE
W s1: ① 累積拉高 0x0F（剛加 bit3）→ ESP_ERR_INVALID_RESPONSE
W s1: ① 累積拉高 0x4F（剛加 bit6）→ ESP_ERR_INVALID_RESPONSE
E s1: ① 全部候選 bit 拉高（0x4F）仍掛不起來——不是 TCA9554 的問題
```

每一次都停在同一個地方：`send_if_cond (1) returned 0x108`。連錯誤碼都沒變過。

### 判讀

**排除兩個假設**：MISO 缺上拉、SD 電源掛在 TCA9554。兩者都試過，錯誤一字不變。

**`config=0x4F` 證實 `board.c` 的用法**：0x4F = `0100 1111`，1 是輸入、0 是輸出，
所以 bit4／bit5／bit7 是輸出（LCD reset、觸控 reset、喇叭功放），其餘為輸入。與程式碼一致。

**`input=0xF7` 有一條線索**：0xF7 = `1111 0111`，**bit3 是唯一的低電位**。
microSD 槽的 card detect 接點通常在插卡時拉低。若 bit3 真的是 CD，這反而佐證卡確實插著。
可用「拔掉卡再讀一次，看 bit3 會不會變 1」來驗證，需要人動手拔插。

**錯誤碼始終如一，指向訊號層而非時序或電源**：`send_if_cond` 是 CMD8，
SD 初始化的第一個握手。卡連一個 bit 都沒回。若是電源或時序問題，
通常會出現不同的失敗點或偶發成功。這種「完全一致的沉默」比較像接線對應錯了，
或那條 MISO 上根本沒有東西在講話。

### ⚠️ 這一輪造成的殘留，必須復原

探測把 TCA9554 的 bit0~3 與 bit6 **從輸入改成了輸出並拉高**。
依 `docs/notes/tca9554-holds-touch-reset.md`：**TCA9554 是獨立晶片，狀態不隨 CPU reset 清除，
只有整片斷電才會回到冷開機狀態。** 所以現在板子上這五個 bit 還維持著輸出高電位。

若 bit3 真的是 card detect（外部訊號源），把它設成推挽輸出等於和外部打架，
可能有持續的短路電流。**下一輪韌體必須先把這些 bit 設回輸入。**

### 下一輪要試什麼

排除了電源與上拉之後，剩下的候選按可能性排序：

1. **腳位對應錯誤**——CS=6 來自既有筆記，CLK=11／CMD=10／DATA=18 來自 BSP 命名推導。
   本專案在 I2S 上踩過同型的坑：BSP 的 `DOUT`／`DSIN` 是以 ESP 為視角而非 codec 視角
   （`docs/notes/bsp-i2s-dout-is-esp-side.md`），SD 的 CMD／DATA 也可能有類似陷阱。
   → 試 MOSI／MISO 對調，成本極低
2. **卡或插槽的實體問題**——讀四支腳位的靜態電位可以判斷有沒有東西接在上面
3. 板子根本沒有可用的 microSD 槽

## 第 3 輪：復原殘留 + 腳位電氣診斷（2026-08-29）

### 這一輪改了什麼

1. `board.c`：新增 `board_exio_release()`，把 TCA9554 的 bit 設回輸入。
   驗證程式開機第一件事就是收掉第 2 輪的殘留。
2. `verify_s1.c`：移除已證偽的 TCA9554 累積拉高（有副作用又沒用），
   換成 `dump_sd_pins()`——對四支腳位分別帶內部上拉與下拉各讀一次電位。
   **判讀規則**：兩次都跟著拉的方向跑＝浮動，沒有外部源；下拉時仍讀到高＝有外部驅動或上拉。
3. `sdcard.c`／`.h`：腳位參數化（`sdcard_mount_pins()`），並公開腳位常數，
   用來試 MOSI／MISO 對調。

### 殘留已收乾淨

```
W s1: TCA9554 開機現況：config=0x4F output=0xFF input=0xF7
W s1: 收掉第 2 輪的探測殘留（bit0~3,6 設回輸入）：ESP_OK
```

`config` 讀回來仍是 0x4F 是對的——0x4F 的 bit0~3 與 bit6 本來就是 1（輸入），
第 2 輪把它們改成 0（輸出），這一輪寫回 1。收乾淨後的值與冷開機一致。

### 結果：MISO 被外部拉低

```
W s1: ①   CS   (GPIO 6)  上拉讀=1 下拉讀=1  → 被外部拉高／有卡在驅動
W s1: ①   CLK  (GPIO11)  上拉讀=1 下拉讀=0  → 浮動（沒東西接）
W s1: ①   MOSI (GPIO10)  上拉讀=1 下拉讀=0  → 浮動（沒東西接）
W s1: ①   MISO (GPIO18)  上拉讀=0 下拉讀=0  → 被外部拉低
W s1: ① 試 MOSI/MISO 對調（MOSI=18 MISO=10）→ ESP_ERR_TIMEOUT
```

### 判讀

**CLK 與 MOSI 浮動不代表沒接。** 這兩支是主機端輸出、卡端輸入（高阻），
沒有外部驅動源本來就會浮動。這兩筆數據沒有排除任何假設。

**CS 被拉高是正常的**——SD 的 CS 慣例上有上拉電阻。

**MISO 被外部強制拉低，這一筆是決定性的。** SD 卡在 idle 時 DO 是高阻或高電位，
**沒有任何情況會把它拉到地**。所以 GPIO18 上現在掛著的東西，行為不像一張通電的 SD 卡。

最能解釋這個現象的是：**卡插著，但卡沒有供電**。未供電的 SD 卡，其 I/O 腳位會透過內部
ESD 保護結構呈現接近 0V 的低阻抗——正好就是「下拉讀 0、上拉也讀 0」。

**對調測試的錯誤碼變了**（`INVALID_RESPONSE` → `TIMEOUT`），證明訊號行為確實隨接線改變，
但兩種接法都不通，所以對調不是答案。

### 新假設：SD 電源掛在 AXP2101 的某個電軌上

排除順序走到這裡，最合理的剩餘解釋是供電。本板的 AXP2101（I2C `0x34`）目前
**只被用來讀電源鍵與軟關機**，從來沒有配置過任何電軌（見 `board.c` 的 `pmic_init()`）。
Waveshare 的板子常把周邊電源掛在 PMIC 的 ALDO／BLDO 上。

### ⚠️ 決策：這一步不自行動手

打開一個用途不明的 PMIC 電軌**有實體損壞風險**——若該電軌的預設電壓設定與接在上面的
元件不符，可能直接燒掉零件。這不是能靠重燒韌體復原的操作。

**因此下一輪只做唯讀**：dump AXP2101 的電軌致能與電壓設定暫存器，把現況攤開來看，
再由使用者決定要不要開、開哪一路。

## 第 4 輪：AXP2101 電軌唯讀 dump（2026-08-29）

### 結果：電軌全開，供電假設排除

```
W s1:   0x80 DCDC enable   = 0x0F
W s1:   0x90 LDO enable 0  = 0xFF          ← 六路 LDO 全開
W s1:   0x91 LDO enable 1  = 0x01
W s1:   0x92 ALDO1 = 0x1C → 3300 mV，開
W s1:   0x93 ALDO2 = 0x1C → 3300 mV，開
W s1:   0x94 ALDO3 = 0x19 → 3000 mV，開
W s1:   0x95 ALDO4 = 0x0D → 1800 mV，開
W s1:   0x96 BLDO1 = 0x07 → 1200 mV，開
W s1:   0x97 BLDO2 = 0x17 → 2800 mV，開
```

**沒有任何一路是關的**，也就沒有「要打開哪一路」的問題。第 3 輪的供電假設不成立，
而且連帶避免了一次有實體風險的寫入——先讀再決定是對的。

有兩路 3.3V（ALDO1、ALDO2）可用，若卡座真的接在其中一路上，卡早就有電了。

### 到這裡，軟體層面的假設全部用盡

| 假設 | 驗證方式 | 結果 |
|------|----------|------|
| MISO 缺上拉 | 開內部上拉 | 排除，錯誤一字不變 |
| SD 電源掛在 TCA9554 | 五個未用 bit 累積拉高 | 排除 |
| CMD／DATA 命名視角顛倒 | MOSI／MISO 對調 | 排除（錯誤碼從 INVALID_RESPONSE 變 TIMEOUT，仍不通） |
| SD 電源掛在 AXP2101 某路 | 唯讀 dump | 排除，全部已開 |

剩下的都不是韌體改得動的：

- **GPIO18 上接的不是一張通電的 SD 卡。** 它被外部強制拉低，而卡有電時 DO 不會這樣
- 所以要嘛腳位對應是錯的，要嘛這片板子的卡座沒有連到這組腳位，要嘛卡座根本不存在

### 決策：交還給人，做一個對照實驗

軟體再猜下去只是發散。最省事的決定性實驗是**拔掉卡再讀一次同一組腳位**：

- GPIO18 的電位**變了** → 卡座確實連在這組腳位上，問題在時序或卡片本身
- GPIO18 的電位**沒變** → 卡座跟這組腳位無關，腳位資訊是錯的（或沒有卡座）

這需要人動手拔卡，韌體代勞不了。同一輪順便把 ②③ 的視覺判定補完
（觀察視窗已從 6 秒延長到 20／15 秒，讓人來得及看）。

## 第 5 輪：拔卡對照實驗（2026-08-29）

使用者拔掉記憶卡，跑同一支韌體讀同一組腳位。

### 結果：完全沒有變化

| 訊號 | 插卡時 | 拔卡後 |
|------|--------|--------|
| CS (GPIO6) | 上拉讀 1／下拉讀 1 | **一樣** |
| CLK (GPIO11) | 浮動 | **一樣** |
| MOSI (GPIO10) | 浮動 | **一樣** |
| MISO (GPIO18) | 被拉低 | **一樣** |
| TCA9554 input bit3 | 0 | **一樣** |

### 判讀

**`GPIO 6/10/11/18` 這一組跟卡座無關。** 插一張卡與不插卡，電氣狀態一模一樣，
代表卡片從來沒有連上這四支腳的任何一支。

順帶否掉第 2 輪的猜測：**TCA9554 的 bit3 不是 card detect**，它在插拔前後都是 0。

### 還沒分辨出來的兩件事

1. 卡座存在，但腳位對應錯了
2. 這片板子根本沒有連通的 microSD 卡座

這兩者的處置完全不同（前者改常數就好，後者要改企劃），必須分清楚。

### 決策：用全 GPIO 掃描來分辨

不需要任何外部資料就能分辨——**插拔卡片會影響哪幾支腳，那幾支就是卡座**。
做法是拔卡與插卡各掃一次所有可動的 GPIO，比對差異：

- 有腳位在插拔之間變化 → 卡座存在，那就是它的腳位，改常數即可
- 完全沒有腳位變化 → 板子上沒有連通的卡座，v3 的記憶卡路線不成立

**掃描要避開的腳位**（動了會當場失聯或當機）：

| 腳位 | 原因 |
|------|------|
| GPIO12／13 | USB D−／D＋，動了序列埠直接斷線，log 也拿不到 |
| GPIO24~30 | SPI flash，動了直接當機 |
| GPIO7／8 | I2C（TCA9554／AXP2101／IMU／codec），掃完要立刻還原 |

掃描在面板拆掉之後進行，所以 LCD 的 GPIO0~5 可以安全掃。

---

## 第 6 輪：全 GPIO 插拔對照（2026-08-29）— 結案

掃描 GPIO 0~23，跳過 7/8（I2C）、12/13（USB）、24 以上（SPI flash）。拔卡與插卡各掃一次。

### 結果：20 支腳位，零差異

```
=== 拔卡 vs 插卡 的差異 ===
→ 完全沒有差異
```

兩次掃描逐支相同：

| 狀態 | 腳位 |
|------|------|
| 外部拉高 | GPIO0、1、2、6、9（BOOT 上拉）、15（TP_INT） |
| 外部拉低 | GPIO18、21（I2S DIN，ES8311 側） |
| 浮動 | GPIO3、4、5、10、11、14、16、17、19、20、22、23 |

### 結論：這片板子沒有連通到 ESP32 的 microSD 卡座

一張 SD 卡插進卡座，至少會在資料線上造成可測量的阻抗變化。**20 支腳位全部零反應**，
代表卡片與 ESP32 之間沒有任何電氣連結。未掃描的腳位不構成漏網：
GPIO7/8 是 I2C（掛著六顆已知晶片）、12/13 是 USB、24 以上是 SPI flash，都不可能是卡座。

`GPIO18` 一直被拉低，與插拔無關，所以它接的是別的東西——旁邊的 `GPIO21` 是 I2S DIN，
同樣呈現外部拉低，兩者行為一致，`GPIO18` 比較可能也屬於音訊或其他周邊，不是 SD DATA。

**CLAUDE.md 記載的 `SD CLK=11 CMD=10 DATA=18 CS=6` 在這片板子上沒有對應的實體卡座。**
那組腳位出自官方 BSP 標頭，BSP 涵蓋整個產品線，不代表手上這片的實際配置。

### 對 v3 企劃的影響

**記憶卡路線不成立**，必須改。而 S1 的驗證本身是有價值的，因為它同時證明了：

| 子項 | 結論 |
|---|---|
| ① SD 掛載 | **失敗（硬體不存在）**——不是韌體問題，改不動 |
| ② 拆 SPI 後畫面保持 | 未判定，使用者兩輪都沒能盯著螢幕 |
| ③ **面板拆裝** | **通過**，多輪皆 `ESP_OK` 且畫面正常重建 |
| ④ 吞吐量 | 不適用 |

**③ 的結論要留下來**：`SPI2` 可以安全地拆掉再裝回去，這是未來要在這片板子上加任何
SPI 周邊時的關鍵前提，與 SD 卡是否存在無關。

### 替代方案：內容改燒進 SPIFFS，走 USB 更新

使用者的核心需求是「不上網」，記憶卡只是達成手段之一，不是目的。改用機身 flash：

| 項目 | 估算 |
|------|------|
| `storage` 分區 | 11MB，目前完全空著 |
| 60 籤語料 | 數百 KB |
| AI 預產解讀（60 籤 × 6 類別） | 1~2MB |
| 子集字型（約 2,500 字 @24px） | ~675KB |
| **合計** | **遠低於 11MB** |

內容更新改走 USB 重燒 `storage` 分區。失去的只有「不接電腦就能換內容」，
換到的是：沒有 SPI 衝突、沒有匯入流程、沒有無卡降級路徑、開機直接讀 SPIFFS。
對一台開發者自用的裝置，這個取捨划算。

## 第 7 輪：修正一個下太快的結論，改用腳位暴力掃描（2026-08-29）

### 先修正第 6 輪的推論錯誤

第 6 輪從「插拔卡片時 20 支 GPIO 電位零差異」推出「板上沒有卡座」。使用者指出這片板子
曾經讀到過卡，回頭檢視，**那個推論站不住**：

> 「一張 SD 卡插進卡座，至少會在資料線上造成可測量的阻抗變化」

這句話對**未初始化**的 SD 卡不成立。卡在收到 CMD0 之前，資料線是高阻狀態，
其內部上拉約 50kΩ，與 ESP32 內部上拉（約 45kΩ）並聯後的分壓變化，
用 `gpio_get_level()` 這種數位讀取根本分辨不出來。**零差異不足以否定卡座存在。**

零差異能否定的只有一件事：那四支腳上沒有**低阻抗**的東西隨插拔出現或消失。

### 改用腳位暴力掃描

不再靠推論，直接窮舉。做法是把候選腳位的所有排列各試一次 `esp_vfs_fat_sdspi_mount()`，
能掛起來就是對的組合。這不依賴任何外部文件。

**第一次候選（7 支）：`6、10、11、14、16、17、18`** — 排除法留下的「沒被其他周邊佔用」者。
7 取 4 共 840 組，實測 38 秒跑完。

```
W s1: ① 開始腳位暴力掃描：7 取 4 共 840 組
W s1: ① 已試 800/840 組
E s1: ① 840 組全部試完，沒有一組掛得起來
```

### 第二個錯誤：候選範圍切太小

排除 `GPIO0~5` 的理由是「那是 LCD QSPI」。但**SD 與 LCD 本來就共用 SPI2**，
板廠讓兩者共用同一組資料線、只用不同 CS 區分，是這類設計的常見做法——
SD CS 標在 `GPIO6`、緊接在 LCD CS=5 之後，正是這種佈線的特徵。
而且掃描時面板已經拆掉，那六支腳是自由的。

**第二次候選（13 支）：`0、1、2、3、4、5、6、10、11、14、16、17、18`**
13 取 4 共 17,160 組，每組約 45ms，全掃約 13 分鐘。

仍然排除的腳位與理由：

| 腳位 | 理由 |
|------|------|
| 7、8 | I2C，掃描期間 TCA9554／AXP2101 還要用 |
| 9 | BOOT 鍵 |
| 12、13 | USB D−／D＋，動了序列埠斷線 |
| 15 | TP_INT |
| 19~23 | I2S（MCK／BCK／WS／DOUT／DIN） |
| 24~30 | SPI flash（`SOC_GPIO_IN_RANGE_MAX = 30`，C6 共 31 支 GPIO） |

### 旁證：原廠韌體 dump 的 BSP 符號

`backup/factory-16MB.bin`（2026-08-06 的 16MB 全片 dump）裡所有 `bsp_` 開頭的符號：

```
bsp_audio_codec_microphone_init   bsp_audio_codec_speaker_init   bsp_audio_init
bsp_board_extra                   bsp_display_indev_init         bsp_display_lcd_init
bsp_display_new                   bsp_display_start_with_config  bsp_extra_board
bsp_extra_codec_init              bsp_extra_codec_volume_set     bsp_extra_file_instance_init
bsp_extra_player_del              bsp_extra_player_init          bsp_extra_player_play_index
bsp_i2c_init                      bsp_io_expander_init           bsp_spiffs_mount
bsp_touch_new
```

**沒有任何 `bsp_sdcard_*` 或 `bsp_sd_*`。** 原廠 app 的檔案系統是 `bsp_spiffs_mount`，
韌體裡確實有 `sdspi_host`／`sdspi_transaction` 這兩個符號，但沒有配套的掛載程式碼，
比較像是 fatfs／player 相依把 IDF 的 sdspi 驅動連帶連結進來的死碼。

**這條旁證支持「原廠也沒在用 SD 卡」**，但不能直接證明卡座不存在——原廠不用，
不等於板子上沒有。真正的判定仍以腳位暴力掃描為準。

### 意外收穫：原廠有麥克風初始化

`bsp_audio_codec_microphone_init` 存在，這對企劃 §8 的 **S7（麥克風是否真的存在且可錄）**
是正面線索——原廠韌體會去初始化麥克風，代表硬體上大概率有。
本專案的 [audio.c](../../src/audio.c) 目前是 `din = I2S_GPIO_UNUSED`，還沒接。
S7 真的要做時，ESP 端的 I2S 輸入是 `GPIO21`（見 `docs/notes/bsp-i2s-dout-is-esp-side.md`），
而第 6 輪的 GPIO 掃描也顯示 `GPIO21` 被外部拉低，與「有東西接在上面」一致。

## 第 8 輪：17,160 組窮舉、板子失聯、結案（2026-08-29）

### 掃描把板子弄到失聯

候選擴大到 13 支（含 `GPIO0~5`）後跑 17,160 組，**掃描期間板子失去回應**：
`monitor.sh` 全程讀不到任何位元組，掃描結果一併遺失，事後連 `esptool` 都
`Failed to connect: No serial data received`。

原因幾乎可以確定是 `GPIO0~5`。那六支是 AMOLED 的 QSPI，面板 `deinit` 之後仍然接電，
被當成 SPI 從機反覆驅動了上萬次。這是**這一輪自己造成的損害**，不是既有問題。

**救援方式**：`esptool` 帶 `--before default_reset` 重新連線後恢復，隨即燒回擲筊韌體。
板子無 RESET 鍵，若這樣不行就要拔 USB、按住 BOOT 再上電，或 PWR 長按硬體斷電。

**教訓**：暴力掃描腳位時，候選裡不能放「接著活躍周邊」的腳。`GPIO0~5` 當初排除是對的，
第 7 輪把它們加回來的理由（SD 可能與 LCD 共用資料線）雖然合理，但沒有評估驅動它們的代價。

### 結案

| 子項 | 結論 |
|---|---|
| ① SD 掛載 | **失敗**。BSP 腳位、7 支未佔用腳的 840 組全滅；擴大到 13 支的 17,160 組因板子失聯而未取得完整結果，但代價已證明這條路不值得再走 |
| ② 拆 SPI 後畫面保持 | **未判定**，使用者數輪都沒能在觀察視窗內盯著螢幕。記憶卡路線取消後此項失去用途 |
| ③ **面板拆裝** | **通過**，多輪皆 `ESP_OK` 且畫面正常重建 |
| ④ 吞吐量 | 不適用 |

**旁證**：原廠韌體 dump 只有 `bsp_spiffs_mount`，沒有任何 `bsp_sdcard_*` 符號。

**處置**：企劃改為內容燒進 SPIFFS、更新走 USB（§5.2、§6）。
分區同時由 `app 4M + storage 11M` 調整為 **`app 6M + storage 9M`**——實測顯示壓力在 app
（圖與字型），語料 JSON 全部加起來不到 1MB，原本的配置是反的（§5.7）。

### 尚未證實也尚未推翻的一點

使用者表示這片板子曾經讀到過卡。本輪所有嘗試都失敗，但**沒有取得反證**——
17,160 組掃描的結果遺失了。若日後想起是用哪支程式讀到的，那份程式裡就有正確腳位，
比任何盲掃都可靠。在那之前，企劃不依賴 SD 卡。

## 附帶產出：語料與 AI 產出的字元守門

籤詩來源原本要參考 `temples.tw`，查證後發現該站 `robots.txt` 明確
`User-agent: ClaudeBot / Disallow: /`，並宣告
`Content-Signal: search=yes, ai-train=no, use=reference`（載明為 EU 2019/790 第 4 條的權利保留）。
`curl` 拿得到 200 而 WebFetch 得到 403，差別只在 User-Agent——**沒有繞過**，
改由人自行查閱校對。站方編寫的籤義另有著作權，不可內嵌進產品。

改為由 AI 產出公有領域的籤詩本文，隨即踩到一個值得記下來的坑：

> 產出的第 5 籤出現 `鬼神дось難測度`——**中間混進了西里爾字母**。

幾百句中文語料裡混入外文字元，肉眼幾乎不可能發現，但會直接變成畫面上的豆腐方塊。
因此 `data/poems.json` 與 `scripts/gen-content.sh` 都加了字元白名單守門
（只允許 ASCII、全形標點、CJK 漢字），違反就中止而不是警告。

同時採取的誠信規則：**沒把握的籤一律 `text: null`，不編造**。
60 首目前只有 3 首有初稿且全部 `verified: false`，其餘 57 首留空等人補齊。
編出來的假籤混在真的裡面，是校對時最難發現的錯誤。

## 附錄：AI 憑記憶產出語料的實測錯誤率（2026-08-29）

使用者提供了自行擷取的 `data/temples-fs60.csv`（63 筆完整資料）之後，

|------|------|
| 1、2、4 | ✓ 完全正確 |
| 7 | △ 2/4 句相符（不用／不須、向前程／問前程、注定／註定） |
| 3 | ✗ 1/4 句 |
| 11 | ✗ 1/4 句 |

| 5 | ✗ 0/4 句，且含西里爾字母污染 |
| 27 | ✗ 0/4 句——**寫的其實是第 47 籤的內容，籤號整個張冠李戴** |

**9 首裡只有 3 首完全正確，正確率 33%。**

三種錯誤型態都出現了，而且一種比一種難發現：

1. **用字出入**（第 7 籤）——四句看起來都對，實際三處用字不同。這種最危險，
   讀起來完全通順，不對照原文根本發現不了
2. **張冠李戴**（第 27 籤）——內容是真的籤詩，但掛在錯的籤號下。
   單看那首完全正確，只有比對籤號才看得出來
3. **字元污染**（第 5 籤）——`鬼神дось難測度`，中文裡混進西里爾字母

當時的處置是對的：**只保留有把握的 3 首、其餘一律留 `null` 不編造**，
而那 3 首事後證明全部正確。若當初「產滿 60 首交差」，就會有 6 首錯誤混進語料，
其中兩種型態校對時幾乎抓不到。

**留下的機制**：`scripts/gen-content.sh` 的字元白名單守門（違反即中止，
只允許 ASCII、一般標點、幾何符號 `○●`、CJK），以及 `poems.json` 的
`verified` 欄位——`gen-content.sh` 在有 `text: null` 或 `verified: false` 時會警告。

**目前狀態**：63 首全數以程式逐首核對過使用者提供的 CSV，
籤詩、干支、卦象、屬性方位 63/63 相符，`verified` 已全部標為 `true`。

### 版權界線

`data/temples-fs60.csv` 保留完整擷取結果供人校對，但 **`poems.json` 只收錄
籤詩本文、干支、卦象、屬性方位**——這些屬公有領域的傳統籤譜資料。

CSV 裡的「籤詩語譯」「籤意」「故事」「籤解」是 temples.tw 編寫的內容，
**不進 `poems.json`、不進 SPIFFS、不進韌體**。本專案要的白話解讀是離線自產的
`ai_readings.json`，本來就不依賴外部來源。
